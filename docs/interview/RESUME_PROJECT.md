# 多 Agent 协同系统 · 一人公司运营平台

## 项目背景
本项目旨在以 OPC 形态为中小企业定制开发 Agent 平台。为突破单人无法覆盖需求分析、开发、部署、客服全链路的瓶颈，研发一套多 Agent 协同系统作为开发团队，以 LLM 驱动的多角色 Agent 承接从需求拆解、开发、部署到客服的完整交付链路。

## 解决方案
- **编排核心**：CEO Agent 基于 LLM 将客户需求拆解为带依赖关系的子任务并生成动态 DAG；执行器经 Kahn 拓扑排序按层并发调度 Developer / Frontend / DevOps 等执行 Agent，依赖关系可按项目定制。
- **工具与记忆**：统一 LLM 路由与工具层，接入代码生成 CLI、Docker 容器化部署与 Nginx 反向代理；以飞书/企业微信承接客户需求与客服问答；使用会话/工作/知识三层记忆，叠加记忆图谱与重要性评分，跨会话召回项目上下文与业务知识。
- **工程保障**：输入校验（Prompt/SQL/XSS 注入）、Docker 沙箱、RBAC 与审计日志；以 Prometheus 指标 + 健康检查 + 告警构建可观测体系；以 Redis 响应缓存（temperature 门控 + 命中率监控）降低重复 LLM 调用成本。

## 项目成果
- 以多 Agent 团队打通需求拆解 → 开发 → 部署 → 客服全链路，支撑独立承接定制开发；
- 构建 11 类埋点、14 项 Prometheus 指标与 6 条告警的可观测与运行报告体系；
- 规避 24 项安全问题（含认证绕过、SSRF、横向越权、沙箱逃逸）。

## 技术栈
Python · FastAPI · asyncio · PostgreSQL · pgvector · Redis · Docker · Nginx · RBAC · Prometheus


在统一llm路由上，我封装了各家大模型的接口，统一为一个方法，当初始化时候，会先经过路由层再被agent调用，这样可以省去agent中再实现接入以及更方便的切换模型。
我希望我设计的agent都有切丝的能够工作实现项目的能力，因此我配备了代码生成cli，就是claude code cli，agent使用该工具时，会传入需求、上下文和工作目录，然后asyncio会启动子进程，利用根据在指定目录中完成修改与实现，并返回result，包括状态、错误、用量信息等。
在我设计的devOps agent中，我希望它能够为我部署项目，因此我为它配备了docker部署的工具，agent收到任务后会先分析项目，并将项目部署到docker上。

我从五个层面控制并发流量。第一，HTTP 回调接口设置频率限制，超限返回429。第二，用Redis原子去重，避免平台重发导致重复处理。第三，企微客服消息先进入Redis队列，将消息接收与耗时问答分开，缓冲突发流量。第四，Worker批量异步消费，与工作流共享五个执行名额，隔离单条任务异常；模型层再统一控制RPM、TPM，并对临时错误退避重试。第五，对符合条件的重复模型请求使用响应缓存，减少模型调用和Token消耗。

1. 总体设计：你的记忆体系是怎么设计的？
我主要想解决两个问题：一是模型上下文有限，不能一直追加历史；二是任务结束后，重要决策和经验需要保留下来。因此我设计了三层记忆：工作记忆用内存保存当前任务的信息；会话记忆通过 Redis 和 PostgreSQL 保存任务历史；长期知识用 PostgreSQL 的 pgvector 保存决策、经验和 FAQ。上层通过 MemoryManager 统一读写，再结合重要性评分、后台提炼和关联图谱，在需要时选择相关信息加入上下文，而不是把全部历史交给模型。

2. 为什么需要三层，而不是全部放进向量数据库？
不同信息的访问方式和生命周期不同。当前任务的消息需要频繁读写，用内存就比较直接；历史任务既需要快速查询，也需要持久保存，所以采用 Redis 热缓存和 PostgreSQL；跨项目经验则更适合按语义检索，放进向量库。分层后，每种存储承担自己擅长的工作，也能避免把临时消息和长期知识混在一起。向量库主要负责找相关知识，不承担所有任务状态和会话记录的管理。

3. 工作记忆具体怎么实现？
工作记忆使用 Python 的 deque，默认最多保存二十条消息，超过容量会自动淘汰最早的信息。它相当于 Agent 的临时白板，保存当前处理过程中观察到的消息和执行结果，读取时不需要访问外部数据库。任务运行结束后，系统尝试把内容归档到会话记忆，归档调用完成后清空工作区。不过当前工作记忆按 Agent 管理，还不能把它描述为严格隔离的每个任务独立工作区。

4. Redis 和 PostgreSQL 为什么要同时使用？怎么保证一致性？
Redis 用来承载近期任务的快速读取，PostgreSQL 用来持久保存历史。写入时系统分别尝试写入两边；读取任务记忆时优先查 Redis，缓存缺失时查询 PostgreSQL，并回填缓存。这样可以兼顾访问速度与历史恢复。不过当前双写没有事务保证，两边可能出现短暂甚至持续的不一致。我把 PostgreSQL 作为持久化依据，但不会声称已经实现强一致；更严格的可靠性还需要补偿重试或对账机制。

5. Redis 保存七天，会不会占满内存？
当前有两项限制：任务详情设置七天 TTL，最近任务索引通过 LTRIM 保留五十条。但五十条只是索引上限，被裁掉索引的详情仍可能保存到过期；聊天记录也没有同样的条数限制。因此 TTL 能限制部分数据的存活时间，不能单独保证内存不会满。容量需要结合七天内写入量、平均记录大小和 Redis 实际内存占用来测算，再配置内存上限与淘汰策略。我目前没有依据承诺固定的内存规模。

6. 重要性评分是怎么做的？为什么这样设计？
我采用一个可解释的启发式评分，把来源角色、记忆类型、内容长度、时间和访问次数五个维度加权，得到零到一之间的分数。目的是让决策和经验比普通聊天更容易被保留和选中。当前权重是人工设定的，内容质量也只是通过长度粗略判断，不代表事实正确。时间维度使用的是随天数下降的函数，不是严格的指数遗忘曲线。这套规则比较容易落地，后续需要通过召回效果评测调整。

7. 记忆提炼怎么实现？会不会影响任务响应？
任务结束后，系统先把工作记忆归档到会话层，再创建后台协程调用模型提炼。提炼结果包括摘要、关键决策、技术要点和标签：摘要用于更新会话记录，决策和技术要点写入长期知识，标签用于建立关联。这样模型提炼不用放在任务返回的关键路径上。但最初的数据库归档仍然需要等待，不能说整个过程完全不阻塞。后台提炼失败时记录错误；目前它也不是带可靠重试的持久化后台任务。

8. 跨会话召回是怎么完成的？
新任务执行时，Agent 可以通过 MemoryManager 检索过去的信息。默认策略结合当前工作记忆、近期任务的关键词匹配和长期知识的语义检索，再去重、排序并选择有限条结果。随后把选出的记忆拼接成上下文，让模型参考之前的决策和经验。不同策略会选择不同的数据来源，例如 recent 偏近期任务，semantic 偏长期知识。这里的跨会话主要依靠持久存储，不是模型本身记住了上一次对话。

9. 为什么设计记忆图谱？它和向量检索有什么区别？
向量检索适合找语义相近的信息，但相关记录不一定使用相同的表达。例如，一条记录描述部署问题，另一条记录描述同类技术方案，文字可能不同却有共同标签。因此我增加了记忆关联图，通过标签等显式关系补充检索上下文。图谱使用 Redis 集合保存关系，并通过 PostgreSQL 持久化，复用项目已有的基础设施。它表达的是关联关系，不是自动推断因果，也不能保证一定找出问题的根本原因。

10. 图谱扩展在你的项目里具体怎么运行？
当前 graph 策略先取得会话任务记忆作为种子，再沿关联边扩展一跳，读取关联记录，并结合重要性和关联权重排序。后台提炼得到标签后，会自动建立同标签记忆之间的关系。代码也提供了同项目建边方法，但目前没有接入自动归档主流程。因此我会把它描述为已实现的轻量关联扩展能力，而不是完整的“向量检索加图谱混合 Graph RAG”；两种检索的进一步融合是后续工作。

11. 怎么防止召回内容再次撑爆上下文？
我没有把所有历史直接加入提示词，而是先限制召回条数，再对每条记忆截取有限长度，并按照估算的 Token 预算拼接上下文。当前每条片段最多取三百个字符，累计超过预算就停止加入。这样能控制历史信息占用的规模，但预算使用字符数量估算，不是模型对应的精确 tokenizer。因此它是上下文控制措施，还需要给系统提示、当前任务和模型输出预留空间。

12. 如何证明记忆有效？现在有哪些不足？
我会用相同任务分别测试开启和关闭记忆，比较任务成功率、历史决策复用情况、回答准确性和 Token 用量，同时人工检查召回内容是否相关。当前已经有召回数量、命中和耗时埋点，但返回非空不代表召回正确，也不能直接证明任务质量提升。当前主要不足包括用户隔离不完整、双写一致性、后台提炼可靠性，以及摘要可能丢失细节。这些都需要通过针对性的评测和工程改进逐步完善。


安全

**1. 总体设计：你的安全体系是怎么设计的？**

> 我把安全设计分成入口认证、输入校验、执行隔离、角色权限和审计追踪五个层面。入口通过 API Key 和平台回调签名确认请求来源；输入层检测常见 Prompt、SQL 和 HTML/JS 注入；执行层将 Claude Code CLI 限制在 Docker 容器中，只挂载指定项目目录，并限制资源和权限；角色层根据 Agent 的职责检查消息处理权限；最后通过审计日志记录关键安全事件和任务结果，让系统既有防护，也能追踪问题发生的过程。

**2. 你怎么防御 Prompt 注入？**

> 我在飞书需求和企微客服消息的处理入口接入 InputGuard。它先检查空内容、长度和零宽字符，再使用 Unicode 归一化后的文本匹配常见攻击模式，例如忽略原有指令、伪造系统身份和工具调用。同时检查编码混淆和 Markdown 隐藏指令。命中规则后拒绝处理，并记录拒绝原因、指标和审计事件。这样可以在外部内容进入 Agent 业务处理之前，拦截已识别的注入特征。

**3. SQL 注入和 XSS 是怎么处理的？**

> SQL 安全分两层：输入层检测 UNION SELECT 等常见注入特征，数据库层使用参数化查询，将 SQL 语句和参数分开，避免用户输入被当作数据库指令执行。针对 HTML 和 JavaScript，我会匹配 script 标签、javascript 协议和事件处理属性等危险内容，并进行替换净化。输入检查负责识别可疑内容，参数化查询负责保护数据库执行边界。

**4. 为什么给代码生成 CLI 加 Docker 沙箱？**

> 代码生成 Agent 不只是输出文本，还会修改文件、执行命令和安装依赖，所以需要限制它能影响的范围。我把 Claude Code CLI 的统一执行入口接入 Docker，每次任务创建临时容器，只将指定项目目录挂载到容器内。这样代码修改能够写回项目，而命令和依赖安装发生在容器环境中。同时设置资源、文件系统和权限限制，降低执行任务对宿主机的影响。

**5. Docker 沙箱具体限制了什么？**

> 文件系统方面，容器根目录只读，指定项目目录可写，临时目录设置 noexec 和 nosuid。资源方面，默认限制两 GB 内存、一个 CPU，并设置进程数量和执行超时。权限方面，移除全部 Linux capabilities，禁止获取新增权限，也不挂载 Docker socket 和宿主机个人目录。任务超时或取消时，会尝试删除对应容器；Docker 不可用时直接返回失败，不转到宿主机执行。

**6. 容器里的模型认证怎么处理？**

> 我通过白名单传递模型所需的认证和配置，例如 API Key、Auth Token、模型名称和接口地址。配置可以来自环境变量、项目配置或 CC Switch 的模型配置，但不会把整个个人配置目录挂入容器，也不会转发数据库、飞书和企微的凭证。认证变量通过权限为六百的临时环境文件传入，避免直接出现在命令参数中，任务结束后删除临时文件。

**7. 你的 RBAC 是怎么实现的？**

> 我为各个 Agent 定义了角色权限白名单，包括允许处理的消息类型、动作和工具。当前在 BaseAgent 的任务入口，会检查消息的 cause_by 是否属于该角色允许处理的范围。例如 Developer 可以接收开发任务，DevOps 可以接收部署请求。检查不通过就停止处理，并记录权限失败事件。这把角色职责转化成代码中的权限规则，减少 Agent 处理超出职责范围的消息。

**8. 外部请求如何认证？**

> 普通业务接口通过中间件检查 X-API-Key，配置认证密钥后，没有合法密钥的请求返回四零一。飞书和企微回调使用各自的平台签名校验：飞书根据密钥和请求内容计算签名，企微先校验签名再解密消息。签名比较使用 compare_digest，减少比较过程中的时序差异。同时，认证失败会进入审计日志，便于定位请求来源和失败原因。

**9. 如何避免平台重发导致重复执行？**

> 我使用消息 ID 作为去重依据，在 Redis 中通过 SET NX EX 原子设置去重标记，默认保留二十四小时。第一次收到消息时设置成功，继续处理；相同消息再次到达时，直接返回应答并跳过业务处理。这样可以减少网络抖动和平台重试造成的重复入队、重复任务以及额外模型调用。原子操作也避免了多个请求同时检查时都认为消息首次到达。

**10. 如何防止恶意回调地址引发 SSRF？**

> 企业微信回调中可能提供 response_url，系统会向这个地址发送回答，所以我在使用之前做 URL 白名单校验。只有符合允许规则的地址才能被请求，可疑地址会被拒绝，并记录安全事件。这样可以限制外部输入决定服务器请求目标的能力，降低访问非预期地址或将回答发送到非预期位置的风险。

**11. 审计日志记录什么？写入失败怎么办？**

> 审计主要记录输入拒绝、认证和权限失败，以及任务执行结果。每条记录包含 Agent、动作、详情和时间，既输出到日志，也写入 PostgreSQL。数据库写入失败时，会记录错误和监控指标，并把事件暂存到默认容量为一百条的内存缓冲区，提供补偿写入方法。任务审计与业务结果分开处理，避免审计写入错误覆盖任务本身的执行结果。

**12. 安全日志和普通运行日志有什么区别？**

> 普通运行日志主要帮助排查程序运行过程，例如哪个节点开始执行、哪个工具出现异常。审计日志则围绕关键操作和安全事件组织，重点记录谁进行了什么操作、权限检查是否通过，以及任务结果。我的项目将审计事件存入数据库，便于按 Agent、动作和时间查询；同时保留运行日志和指标，帮助把业务执行过程与安全事件关联起来。

我会在调用llm前，先将请求摘要、模型名称和温度组合后计算键值，检查redis缓存来进行匹配，计算能否有可以直接输出的答案。

*企业微信 CEO 应用*

**我给 CEO 应用发一条消息时，整条链路会发生什么？**

> 我在企业微信 CEO 应用里发一条文字后，消息会进 `POST /api/wecom/ceo/callback`，在这一次请求里问完模型再回给我。它不会拆任务，也不会叫其他 Agent。
>
> 1. 企业微信把消息加密后 POST 到这个地址，查询参数里带 `msg_signature`、`timestamp`、`nonce`。这个接口限流是每分钟 120 次。
> 2. `WecomClient.decrypt_message()` 先验签，再用 `WECOM_CEO_TOKEN` 和 `WECOM_CEO_AES_KEY` 解密。解出来优先当 JSON（智能机器人），否则当 XML。签名失败就直接返回错误，后面都不走。
> 3. 只处理文本。事件消息直接回 `{"code": 0}`。图片、语音等没有正文的，返回空消息错误。
> 4. 用消息 ID 做 Redis `SET NX`，键是 `wecom_ceo:{msg_id}`，保留 24 小时。同一条再推过来就跳过。Redis 不可用时退回进程内的 set。
> 5. 取出 CEO Agent，调用 `_get_general_answer(原文)`。这里不经过 `InputGuard`，也不做意图分类，不查进行中的计划。
> 6. 这一步同步调 DeepSeek。系统提示里拼上 `soul.md`、`product.md`，以及 `/root/` 下各项目的 `claude.md`、`product.md`（各截约 500 字）。对话只有系统提示和这一句，没有上一轮。回复上限约 500 token。模型失败就回那句固定的「我是 CEO Agent，请发送客户需求开始」。
> 7. 答案不写在给企业微信的 HTTP 响应里。代码检查消息体里的 `response_url`：必须是 `https`，主机在 `qq.com`、`tencent.com`、`weixin.qq.com` 上，并解析 DNS 排除内网地址。通过后用 `httpx` 向这个地址 POST 一条 markdown。没有 `response_url` 时，答案算出来了也不会发出去。
> 8. 最后给企业微信回 `{"code": 0}`，表示这条回调处理完了。聊天里看到的那条字，来自第 7 步，不是这个返回值。

*FastAPI*

当客户端向服务端发送一个请求的时候，先经过Nginx代理（如有）转发，然后到达指定的服务端，服务端解析请求按照asgi约定交给fastapi，然后fastapi根据接收到的请求寻找路由，验证材料，如通过后就调用对应的函数，等待结果后回传给uvicorn，然后再由uvicorn回传给客户端。
