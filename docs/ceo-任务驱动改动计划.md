# CEO 任务驱动改动计划

改动按这个顺序做。先让 CEO 能产出需求文档并控制执行，Agent 内部的自驱循环留到下一轮再收。

## 1. 计划结构

文件：`models/task.py`

`ProjectPlan` 增加 `design_doc`，由 CEO 写成的需求文档。`Task` 增加 `acceptance`，写明做完要交出的产物。Redis 里的 `to_dict` / `from_dict` 一并带上这两个字段。

## 2. 模板只保留能力

文件：`templates/project_template.yaml`

删掉固定阶段和「每阶段必须有人、下一阶段必须依赖上一阶段」这些规则。模板只留下 Developer、Frontend、DevOps 各自能做什么、交付什么。有没有前端、要不要部署，由需求文档决定。

## 3. CEO 先写文档，再调配

文件：`agents/ceo/agent.py`

新需求进来后分两步调用模型：

- 用这次需求，加上 `product.md` 和当前会话里已有的计划上下文，写出 `design_doc`。
- 只按文档里真正要做的事生成任务：角色、说明、依赖、`acceptance`。

确认卡片展示文档摘要和任务列表。老板提出修改时，两步一起重来。`/api/requirement` 走同一条拆解路径。

需求文档写完后，由 CEO 为该客户创建一个长期容器，并把文档写入容器内的 `/workspace/需求文档.md`。容器只作为这个客户的工作区，不在里面安装数据库。后续任务都带着容器名和数据卷。`design_doc` 字段保留文档路径和正文，供确认卡片和 Redis 恢复使用。

## 4. CEO 控制执行，执行器只派工

文件：`agents/ceo/agent.py`、`workflows/executor.py`

CEO 按依赖找出当前可执行的任务，把客户容器里的需求文档、该任务说明、`acceptance` 和上游产物交给执行器。执行器只调用对应 Agent，把结果交回。CEO 对照 `acceptance` 标记完成、失败或跳过下游，再派下一批。执行中途不再整图交出去直到结束。

## 5. 这一轮不动 Agent 内部

Developer 仍会在收到任务后自己拆分。等上面的任务消息稳定后，再单独收它的自驱循环，让它只执行被派到的那一项。

## 后续设定（本轮不实现）

客户注册之后才拥有自己的容器。未注册的客户不分配任务，也不进入客服流程。容器由 CEO 在写需求文档时创建；平台数据库仍是共享服务。
